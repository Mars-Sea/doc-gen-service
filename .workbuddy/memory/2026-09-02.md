# 2026-09-02

## Word 文档生成模块代码审计

对 Word 生成全链路（`DocController` → `WordService` → `ImagePayloadConverter` / `TemplateValidationUtil`）
做了完整审计，产出 `WORD_GENERATION_AUDIT.md`（项目根目录）。

**方法**：静态分析 + 编写可运行复现程序实测（3 个程序，`C:\tmp\wordrepro\`）。
未安装 Maven，通过 `javac` + 本地 `~/.m2` 仓库构建 classpath 直接编译 `src/main/java` 与复现程序。

**实测确认的 9 个问题**（详见报告）：
1. 【高】`buildRenderConfig` L264 无条件把 Iterable 数据绑定 `LoopRowTableRenderPolicy`
   → 模板中列表变量在表格外时抛 `RenderException` → 500。poi-tl 按标签名匹配策略，不校验是否在表格内。
2. 【高/安全】`ImagePayloadConverter.downloadImage` 无主机白名单 → SSRF（可访问 127.0.0.1/内网/云元数据）。
   协议白名单（仅 http/https）实现正确，但挡不住 host。
3. 【高】`LOOP_ROW_TAG` 正则 `\[[^\[\]{}]+\]` 过宽 → 表格中 `{{tag}}` 行的下一行含任意 `[...]`
   （如 `[选填]`）且该 tag 数据缺失时，下一行被静默删除。
4. 【中】`validateWordTemplateExtension` 放行 `.doc` → `OLE2NotOfficeXmlFileException` → 500（应 400）。
5. 【中】`detectLoopTableFields` 的 `catch (IOException)` 失效 —— POI 的 `OpenXML4JException`
   是**非受检**异常，模板损坏时容错降级不生效。
6. 【中】循环数据缺失时，poi-tl 只删 `[field]` 数据行，保留 `{{items}}` 触发行为空行（与注释承诺不符）。
7. 【中】`preprocessImagePayloads` 仅顶层扫描 → 表格循环行内图片载荷渲染为 `Map.toString()`。
8. 【中】图片格式依 Content-Type 推断，不校验魔术字节 → 错配时嵌入损坏图片。
9. 【中】`generateBatch` 逐条 `merge()`，内部 `generate(true)` 全量重建 → O(n²)；
   实测 800 条 51 秒 / 峰值堆 261MB，且无条数上限。

## poi-tl 1.12.1 关键机制（源码核实结论）

- `LoopRowTableRenderPolicy.getTemplateRowIndex()` = 标签行 + 1，即 `{{items}}` 在触发行、
  `[field]` 在**下一行**。项目 `TemplateInitializer` 生成的模板结构符合此约定。
- `RunTemplate.findPolicy()` = `config.getCustomPolicy(tagName)`，**按标签名匹配，与位置无关** —— 缺陷 1 根源。
- `NiceXWPFDocument.merge()` → `XmlXWPFDocumentMerge.merge()` 末尾 `source.generate(true)`：
  关闭旧文档并返回全新文档（项目注释正确），但代价是每轮全量序列化+反序列化。
- `Configure.builder().useSpringEL()` = `useSpringEL(true)`（严格），会被后续
  `setRenderDataComputeFactory` 覆盖 —— 项目中该调用是死代码。

## 环境备忘

- 本机**未安装 Maven**（无 `mvn`、无 `mvnw`），Java 21。
- 复现方案：`find ~/.m2/repository -name "*.jar" | tr '\n' ';'` 生成 classpath，
  再用 `javac`/`java` 直接跑。Lombok 在 classpath 上即可自动作为注解处理器。
- **坑**：Windows 版 `javac`/`java` 把 Git Bash 的 `/tmp` 解析为 `C:\tmp`，
  `-d /tmp/x` 会写到 `C:\tmp\x`。统一使用 `C:/tmp/...` 形式的绝对路径。

## 测试执行方案（无 Maven 环境跑 JUnit 5）

- `~/.m2` 中有 `junit-platform-launcher`/`jupiter-engine`，写 `JUnitRunner.java`（Launcher API + SummaryGeneratingListener）执行全部测试类。
- **坑 1**：手工 classpath 混入 slf4j-api 1.7.32/1.7.36 与 2.0.9，旧版在前导致 Spring Boot 3 上下文加载失败（NOPLoggerFactory）；剔除 `slf4j-api/1.7.*` 即可。
- **坑 2**：javac 必须加 `-parameters`，否则 `@PathVariable` 无参数名元数据 → MockMvc 测试 400（IllegalArgumentException: Name for argument not specified）。Maven 的 spring-boot-starter-parent 默认带此参数。
- 最终结果：7 个测试类 **131 个测试全部通过**（含 WordServiceTest 循环表格、模板校验、图片转换、Controller MockMvc）。
- JUnitRunner 位于 `C:/tmp/build/JUnitRunner.java`，classpath 缓存 `C:/tmp/wordrepro/cp.txt`。

**新发现（此前 Word 审计未覆盖）**：
1. 【严重】`com/deepoove/poi/xwpf/` 补丁类（Abstract/XmlXWPFDocumentMerge，499 行）被 git 跟踪但不参与 Maven 构建（pom 无 sourceDirectory，target/classes 与 jar 均无），运行时实际用 poi-tl 官方 jar 同名类 —— 幽灵代码，需纳入构建或删除。
2. 【严重】全接口无认证授权（无 spring-security、无 API Token），模板上传可静默覆盖（REPLACE_EXISTING）。
3. 【一般】GlobalExceptionHandler 的 Exception 兜底接管 HttpMessageNotReadableException / MaxUploadSizeExceededException 等 → JSON 解析失败/上传超限返回 500 而非 400/413。
4. 【一般】XWPFTemplate 在 try-with-resources 赋值表达式中 compile+render，render 抛异常时 template 不关闭 → 资源泄漏。
5. 【一般】ExcelService.preprocessImagePayloads 只转顶层 data 图片，listData（{.field} 行内）不转 —— 与 Word 端递归转换不一致。
6. 【一般】TemplateService.uploadTemplate 直接 Files.copy(REPLACE_EXISTING) 非原子；TemplateValidationUtil 未拦 Windows 盘符冒号。
7. Go SDK：createFile 全局 var + init() 覆盖属过度设计；template.go 六段重复错误处理；无单元测试。
8. SSRF（缺陷 2）本次再次确认为未修复项；/word/batch dataList 无上限 + 全内存 merge 的 OOM 风险与此前 o(n²) 实测结论一致。
9. 工作区有大量未提交删除（.agents/.claude/.codex/.pi 等 Trellis 遗留），已提醒用户提交清理。
