# 决策记录

记录会影响后续输出的关键决策。条目编号按章节独立编号。

## 一、模板寻址收敛（2026-10-02）

### 1.1 深化 `TemplateService`，而非新建平行模块

把模板寻址收敛为一个深模块时，没有新建与 `TemplateService` 平级的 `TemplateStore`。`TemplateService`
原有 5 个方法里，除上传的校验与落盘外，其余全是对文件系统的定位与读写——它本来就是「寻址」概念的栖身
之所，只是 `WordService` / `ExcelService` 没走它。再造一个新模块只会多出一个浅模块（接口与实现几近同
宽），恰是本次要消灭的东西。

### 1.2 接口拆为读侧与写侧

最终形态为 `TemplateRepository`（读：`locate` / `read` / `list`）与 `TemplateWriter`（写：`upload` /
`delete`）。二者分开的真实理由是错误语义不同：读侧找不到文件是 `TemplateNotFoundException`，写侧收到
非法输入是 `IllegalArgumentException`。

命名规则与基路径读法仍只有一份，见 1.3 与 1.4。

### 1.3 命名规则做成不可变值对象，而非校验工具类

`TemplateName` 只由 `parse(raw, kind)` 产出，实例即「已合法」。没有沿用 `TemplateValidationUtil` 那种
`void validate(...)` 的形态——那种形态把规则集中到了一处，但未校验的名字照样能传到接口上，「合法」取决
于调用方自觉，这正是历史上三套校验并存的根因。

### 1.4 字符规则用白名单，不用黑名单

原实现沿用一个坏字符补一次的黑名单（`..`、`/`、`\`），漏掉了 Windows 盘符冒号。白名单用
`\p{L}\p{N}_.-`，中文模板名保持合法，空格与控制字符落选。

### 1.5 `.xls` 一律拒绝

事实核查结论：EasyExcel 4.0.1 对 `.xls` 模板技术上走得通（`WriteWorkbookHolder` 按扩展名推断
`ExcelTypeEnum.XLS`，`WorkBookUtil.createWorkBook` 走 `HSSFWorkbook`），但上传入口硬编码只收
`.docx`/`.xlsx`、列表入口也只列这两种——`.xls` 根本进不了模板目录，校验层的放行是死路。

且全库从未存在过 `.xls` 文件，git 历史 0 命中，测试只有一条字符串断言。据此判定它是未完成的意图而非
正在用的能力，故生成侧改判为只认 `.xlsx`。

### 1.6 `DocGenProperties` 只由读侧持有

`WordService` 与 `ExcelService` 原先持有它只为 `getTemplatePath()`，收敛后已成为接口上的假依赖，故移
除（构造参数分别从 3→2、2→1）。写侧不算目标路径，改为通过 `TemplateRepository.resolveForWrite` 取，避
免基路径读法被复制成两份。

### 1.7 上传侧沿用字符清洗，寻址侧用白名单

两侧规则刻意不同：上传的人是手里拿着文件的人，名字常带空格与括号，因一个空格拒绝整个文件不合理。由
此保证一条不变量——**凡是能落盘的名字，之后一定能在读侧被合法解析**，并有测试锁定。

### 1.8 删除 `templateExists`

生产代码无调用方（控制器四个端点均不走它），只有 2 个单元测试在用。删除它复杂度不会回来，属通过删
除测试的浅方法。

### 1.9 错误消息去掉服务器绝对路径

`TemplateNotFoundException` 原消息为 `"Template not found at: " + templatePath`，绝对路径经全局异常处
理器进入响应体，等于对外暴露服务器目录结构。改为只含模板名——模板名是调用方自己传的，回传它无泄露却
是排障必需。

### 1.10 迁移测试而非复制

穿越接缝的 5 个用例（`WordServiceTest` 3 例、`ExcelServiceTest` 2 例）平移到新测试类后删除。理由：接
口即测试面，契约由深化后的模块的测试保证；三个调用方各自保留同一条断言，只是在三个地方锁同一个事实。

## 二、载荷设施收敛（2026-10-02）

### 2.1 遍历器与转换结果提为独立模块

新增 `PayloadWalker`（遍历渲染数据树：嵌套 Map、Iterable、数组三类容器）与 `ConvertedImage`（载荷转换的
统一出口：字节 + 格式 + 宽高）。原先遍历逻辑内嵌在 `WordService.convertImagePayload`，Excel 侧另有一份
只扫顶层且 listData 分支完全不做预处理的副本。

`ConvertedImage` 提为独立类型而非让 `QrCodePayloadConverter` 反向 import `ImagePayloadConverter` 的嵌套
record，避免 util 包内不自然的横向依赖。

### 2.2 数组是遍历的独立一支

Java 中数组不实现 `Iterable`。原实现在 `Object[]` 上漏掉这一支，导致 `items[0].logo` 保持 Map 原样并
被渲染成 `Map.toString()`，与「只扫描顶层」是同一种静默失败。已补并有测试锁定。

### 2.3 Excel 侧补齐列表载荷与二维码

事实核查结论：EasyExcel 4.0.1 的 `fill(List)` 列表路径与 `fill(Map)` 单值路径走同一个 `doFill` /
`converterAndSet` / `fillImage`（`AbstractExcelWriteExecutor.convert` 判 `originalFieldClass ==
WriteCellData.class` 后原样返回），两者等价。故缺口在自身代码：`listData` 分支未做载荷转换。

二维码此前仅 Word 支持，其字节由 ZXing 本地生成、无 URL，无法走图片的 HTTP 下载链路，故为其新增字节级
出口 `convertToImage`，与图片共用 `ConvertedImage`。

### 2.4 附件响应收敛为一个模块

新增 `GeneratedDocumentResponse`，DocController 四个端点改为交出「内容 + 用户想要的文件名」。事实核查
确认 Go SDK 完全不读 Content-Disposition（`doPostRequest` 只读 body，保存文件的文件名来自调用方
`outputPath`），故无向后兼容风险。`TemplateController.downloadTemplate` 未纳入——其 templateName 已由
`TemplateName` 白名单校验，本身安全，改它属风格统一而非修复问题。

## 三、未纳入本次的已知缺陷

以下缺陷本轮已识别但未处理，留待单独排期：

### 3.1 上传非原子

`Files.copy(REPLACE_EXISTING)` 直接覆盖目标文件，并发「渲染读取 + 上传覆盖」可读到半写文件。修复会改
变 `upload` 的失败语义，需单独确认。

### 3.2 日志注入

`fileName` / `templateName` 等用户输入未做换行过滤即入日志。波及全部 controller 的日志行，超出模板寻
址这条线。

### 3.3 `GlobalExceptionHandler` 兜底处理器接管 Spring MVC 内建异常

JSON 解析失败、405、multipart 超限都会落入兜底返回 500，与文档承诺的 400/413 不符。

详见 `CODE_REVIEW.md` 对应章节。

## 四、管理页面（2026-10-09）

### 4.1 静态单页，不加模板引擎与前端构建

`src/main/resources/static/` 下放 `index.html` + `app.js` + `styles.css`，原生 `fetch` 调现有接口。
未引入 Thymeleaf、未引入 Node 构建：本仓库的构建契约是「一条 `mvn clean package` 出 jar」，
引入前端构建就得把产物再拷一次回 `static/`，与Dockerfile 的 `COPY target/*.jar` 不再自洽。
Spring Boot 在存在 `static/index.html` 时自动把 `/` 映射为欢迎页，Swagger 的 `/swagger-ui.html`
不受影响（实测 302 后 200）。

后端改动为零：不加依赖、不加 Controller、不改任何业务逻辑，页面只消费现有四个模板接口。

### 4.2 挂载在根路径 `/`

与「API 服务另挂 `/admin`」二选一，取根路径：服务本身除 Swagger 外没有别的门户页，`/` 404 只
是让首次访问者多猜一次。

### 4.3 不做鉴权

现有全部 API 本就无鉴权，单独给页面加口令会造出「页面有锁、接口无锁」的假象。要加应整体加，
属独立议题。

### 4.4 列表元数据（2026-10-09 补记，已由第五章取代）

初版只返回文件名数组，界面因此无法显示大小与修改时间。随后按第五章补上了元数据，
本节保留仅为记录当初「暂不做」的缘由：补元数据需改 `list()` 的返回结构，影响 Go SDK。

**现行设计见第五章。**

### 4.5 同名覆盖的判断放在前端

服务端 `upload` 是覆盖语义（`Files.copy(REPLACE_EXISTING)`），改成拒绝会改变其失败语义（见 3.1）。
故前端在列表里查到同名时先弹确认，用户确认后才发包；服务端行为不变。

### 4.6 下载走 `fetch` 而非直接跳转

下载接口失败时返回的是 JSON 错误体。直接跳转会让浏览器把错误体存成一个文件，用户看不到原因；
走 `fetch` 才能读出 `message` 显示为中文提示。

### 4.7 上传成功回显服务端落盘名

服务端会清洗文件名中的非法字符（见 1.7），落盘名可能与用户选的原文件名不同，故提示条回显
`fileName` 字段而非本地文件名。

## 五、列表元数据（2026-10-09）

管理页面要显示大小与修改时间，而 `GET /api/v1/template/list` 原先只返回文件名数组。
本节记录补上元数据时的取舍，取代 4.4 的「暂不做」。

### 5.1 直接把 `templates` 改为对象数组，不做兼容

元素从文件名字符串改为 `{name, size, lastModified}`。备选是「保留旧字段 + 另加 details」或
「新增独立端点」，二者都不破坏旧客户端，但代价是同一份事实在响应里出现两次（或两处列表逻辑
各自漂移）。这是破坏性变更——Go SDK 用 `[]string` 反序列化会直接报错，故同一轮一并改了 SDK，
不留半新半旧的中间态。

### 5.2 引入 `TemplateInfo` 值对象，而非让 `list()` 返回 `Map`

`list()` 返回 `List<Map<String,Object>>` 也能出同样的 JSON，但那样控制器之外就没有「一条模板信息」
这个类型，任何将来要复用它的地方都只能重新拼 key。`TemplateInfo` 由读侧产出、包外不可构造，
实例即「这些属性确实是从该文件读出来的」。

### 5.3 时间统一 ISO-8601 UTC，不带服务器本地偏移

带偏移（如 `+08:00`）读起来直观，但跨时区调用方要么解析它、要么猜；UTC 的 `Z` 形式是唯一无需
猜测时区基准的写法，客户端按本地时区展示即可。用 `Instant` 表达并在控制器里显式 `toString()`，
避免 `Instant` 的序列化结果受全局 Jackson 配置影响而变形。

### 5.4 时间截断到秒

文件系统给出纳秒精度（`2026-10-09T09:31:52.161164400Z`），而「模板什么时候改的」这一问法只到秒
为止；留着尾数只会让每次列表响应都不同、无法比对。截断在 `TemplateInfo.of` 内完成，测试锁定。

### 5.5 只返回字节数，不返回人类可读文本

`"20 KB"` 看着方便，但同一事实两处表达迟早不一致，且单位换算规则（1024 还是 1000、保留几位）
要在服务端与每个客户端之间保持一致。换算属展示层职责，交给各客户端按自己的语言与习惯做。

### 5.6 单个文件属性读失败不中止整个列表

一个文件被占用读不出属性，不代表其余模板不可用。此时大小回退 0、时间回退 epoch，
而不是让整个列表接口 500。

### 5.7 删除 Go SDK 的 `ListTemplatesWithDetails()`

它存在的唯一理由是拿完整响应体；`ListTemplates()` 现在返回完整元数据后，它只剩「多包一层
success/count」的重复。删掉同时消掉了 `CODE_REVIEW.md` 里记的复制粘贴问题的一半。
`ListTemplates()` 返回值类型随之改为 `[]TemplateInfo`。

### 5.8 前端兼容旧的纯字符串元素

页面对 `templates[i]` 是字符串还是对象都做了处理，取不到元数据时显示 `-`。理由不是「要兼容旧
服务端」，而是页面与服务端是同一次发布的两个产物，部署不可能严格同时完成，中间态不该白屏。

## 六、Excel 填充的内存边界（2026-10-26）

线上 `/api/v1/doc/excel/fill` 抛出 `OutOfMemoryError: Java heap space`，堆栈落在
`ExcelService.fillTemplate` → `ExcelBuilderImpl.fill`。本章记录由此引入的限额、OOM 处理与
图片去重，以及刻意没做的部分。

### 6.1 根因是三道闸门同时缺位，不是某一行代码写错

1. **请求体没有体积上限。** `spring.servlet.multipart.max-request-size` 只作用于 multipart 请求，
   Tomcat 的 `maxPostSize` 只作用于 `x-www-form-urlencoded`；而文档生成端点收的是
   `application/json`，此前没有任何一层管到它。
2. **列表行数没有上限。** `ExcelFillRequest.listData` 只有 `@NotBlank` 级别的约束，行数任意。
3. **模板填充本身是全内存模型。** EasyExcel 4.0.1 的 `WorkBookUtil.createWorkBook` 在带模板时
   必定 `new XSSFWorkbook(templateInputStream)`，`WriteWorkbookHolder` 还先把整份模板读成
   `byte[]`；填充全部落在 `getCachedSheet()`（XSSFSheet）上，SXSSF 的流式窗口对 `fill` 不生效。
   行数直接线性映射成堆占用。

### 6.2 限额默认不启用，由部署方按环境给出

`docgen.limits.*` 四项默认全部 `-1`。理由：合适的数值取决于部署机的堆大小与真实业务量，代码里
硬编码一个数字等于替部署方猜，猜小了误伤正常业务、猜大了等于没设。限额在
`ExcelService.checkLimits` 里于填充**开始之前**判定——一旦进入填充流程再发现超量，堆已经被占住，
拒绝请求也救不回来。

三项分开判定而非合成一个「总重量」：行数决定工作表要建多少行对象，字段数决定单值填充的单元格
数，图片张数决定 `addPicture` 要往包里写多少份字节，任一维度失控都足以吃满堆。

**代价必须写明：默认不启用意味着默认情况下这次的 OOM 仍会复现。** 代码到位只是让「打开开关」
成为可能，真止血需要在 `docker-compose.yml` 里取消对应环境变量的注释。

### 6.3 请求体上限在读取时计数，不看 `Content-Length`

`RequestBodySizeFilter` 把 `getInputStream()` 包成带计数上限的 `ServletInputStream`，超过阈值
即抛 `PayloadTooLargeException`。不看 `Content-Length` 是因为分块传输（chunked）的请求没有该头，
只看头会漏；只包 `getInputStream()` 不够，`getReader()` 也一并覆盖，否则表单类转换器有绕过路径。

超限时抛异常而不是截断返回：截断会让 JSON 解析报出一个与真实原因无关的语法错误，掩盖
「请求太大」这个事实。

注册顺序取 `HIGHEST_PRECEDENCE`：Jackson 反序列化发生在 `DispatcherServlet` 内，过滤器排在它
之后时超量请求体已经被读进内存，限额失去意义。

### 6.4 不设 `-XX:+ExitOnOutOfMemoryError`

它与「catch OOM 给客户端 503」互斥：该参数在 OOM 抛出的那一刻直接终止进程，`catch` 与
`GlobalExceptionHandler` 都不会执行，客户端看到的是连接被重置。

选择保留 catch：`OutOfMemoryError` 是 `Error`，Spring 的 `@ExceptionHandler(Exception.class)`
兜底接不住，不就地转换的话调用方只会拿到断连、日志里也看不出是「数据太大」。捕获后进程未必可用
——堆满时 GC 通常能回收出空间，但也可能进入持续 OOM 的半死状态，那种情况由容器的
`restart: unless-stopped` 兜底。因此 `DocumentGenerationException` 只负责「让当前请求得到明确
答复」，不声称进程已恢复。

### 6.5 `docker-compose.yml` 加 `mem_limit`

不设容器内存上限时，JVM 按宿主机总内存推算堆大小，容器内看到的宿主内存可能远大于实际可用量，
最终表现为进程被 cgroup 杀掉而不是抛出可捕获的 `OutOfMemoryError`。取 2g 起步，按实际负载调整。

同时开启 `-XX:+HeapDumpOnOutOfMemoryError` 并把 `/app/dumps` 挂载到宿主机：OOM 快照是排查
「哪个请求、哪份数据撑爆的」的唯一直接证据，留在容器内会随重启消失。

### 6.6 图片按 URL 与 SHA-256 两级去重

`ImageCache` 作用域是一次 `fillTemplate` 调用，不跨请求共享——图片字节与请求数据同生共死，
缓存越过请求边界就变成没人回收的常驻内存，与本类要解决的问题正好相反。

- **URL 键**：同一张图在多行重复出现时只下载一次，省网络往返与下载途中的临时缓冲。
- **内容哈希键**：不同 URL 指向同一份字节（CDN 多域名、带签名参数的同一资源）时，堆里只留一份
  `byte[]`，后续单元格复用同一个数组引用。用 SHA-256 而非 `Arrays.hashCode`：后者 32 位，对
  「图片字节」这种高度相似输入碰撞概率不够低，碰撞会导致两张不同的图被当成同一张，静默出错图。

**本类不能做到的事必须写明：** EasyExcel 的 `AbstractExcelWriteExecutor.fillImage` 内部无条件调
`workbook.addPicture(bytes, type)`，POI 每次新建一个 `PackagePart` 并写出字节。这一步在库内部，
外部无法拦截，所以最终 xlsx 里同一张图仍会存多份。去重减少的是服务端堆里的副本数与下载次数，
不是产出文件的体积。要真正省下这部分，得自己接管 `fillImage`（自定义 `CellWriteHandler` 或绕过
EasyExcel 图片路径），复杂度与风险都高一个量级，本次不做。

### 6.7 `forceNewRow(TRUE)` 本次不动

`FillConfig.forceNewRow(TRUE)` 会让 `ExcelWriteFillExecutor.fill()` 在填充前调
`sheet.shiftRows(...)`，而 POI 的 `XSSFSheet.shiftRows` 每次都要遍历全部行、`rebuildRows()`
把所有 `CTRow` 塞进 `TreeMap` 重建。每遇一个列表占位就 shift 一次，复杂度近似
O(占位数 × 总行数)，是本次 OOM 的主要贡献者之一。

本次不动它，因为它同时决定模板语义：`FALSE` 是原位扩展，模板里列表占位行下方的静态内容不会被
下推，可能被覆盖。改它需要先定「列表行下方还有静态内容」的处理策略（模板自检并拒绝 / 仅文档
标注 / 做成请求参数），属于独立议题。收益因此打了折扣——限额挡住的是超量请求，没有让单请求变快。

### 6.8 兜底异常响应不再透传 `e.getMessage()`

底层异常消息常带服务器绝对路径、SQL 片段、上游英文错误码，对调用方无意义且属于信息泄露
（`CODE_REVIEW.md` 2.1 节记过这一项）。真实原因已记入日志，响应只给可读概括。这一改动同时
覆盖了所有端点的兜底 500，不只是 Excel。

### 6.9 输出仍走 `byte[]`，不改流式

`ByteArrayOutputStream` 装整份 xlsx 后 `toByteArray()` 再复制一份，峰值是文件大小 ×2。改
`StreamingResponseBody` 能降一半，但要处理临时文件清理与客户端中断时的异常路径，且会改变
HTTP 契约的写出方式。本次不动，留作后续独立改动。

### 6.10 修正 `preprocessListPayloads` 的失效注释与死代码

原注释声称「逐个元素处理是为了让字段路径带上行号（`items[0].logo`）」，实际
`preprocessImagePayloads(row)` 每行都从字段名重新起头，路径里根本没有行号，异常提示定位不到
具体行；同时方法内 `int index` 只增不用。注释已按实际行为改写，死变量已删。

## 七、十万条导出的容量结论（2026-10-26）

需求方提出「一次性导出十万条」。本章记录实测结论与由此做的参数化，不涉及技术路线变更。

### 7.1 实测数据（本机，20 列中文长文本）

| 路径 | 堆上限 | 10 万行 | 耗时 | 产出 |
|---|---|---|---|---|
| `POST /api/v1/doc/excel` | 1 GB | 成功 | 7.8 秒 | 6.7 MB |
| `POST /api/v1/doc/excel/fill`，`forceNewRow=true` | 1 GB | **OOM** | — | — |
| 同上 | 1.5 GB | **OOM** | — | — |
| 同上 | 2 GB | 成功 | 20 秒 | 6.2 MB |
| 同上，`forceNewRow=false` | 1 GB | 成功 | 2.7 秒 | 0.8 MB |

窄表（6 列）下两条路径 1 GB 都能跑完：生成 2.8 秒、填充 7.8 秒。

### 7.2 `forceNewRow` 是填充路径 OOM 的唯一决定性因素

同一份数据、同一个堆上限，只改这一个布尔值：所需堆从 2 GB 降到 1 GB，耗时从 20 秒降到
2.7 秒，产出从 6.2 MB 降到 0.8 MB。

原因在 POI：`true` 时 EasyExcel 填充前调 `XSSFSheet.shiftRows()`，每次都要遍历全部行、
`rebuildRows()` 把所有 `CTRow` 塞进 `TreeMap` 重建，且行对象全程驻留堆。体积差异来自 shift
出来的空行也被写进了文件。

### 7.3 `forceNewRow` 做成请求参数（默认值后改为 `true`，见 7.9）

它同时决定内存成本、耗时与产出体积，服务端无法替调用方判定：`false` 是原位扩展，模板里列表占位
行**下方**的静态内容（合计行、备注、签名区）不会被下推、可能被覆盖。因此做成
`ExcelFillRequest.forceNewRow`，由调用方按模板与数据量选择。

本节最初的默认值是 `false`，理由是「不让所有调用方为少数模板的布局需求付 5 倍耗时」。
该结论只看了耗时，没看产出能否打开，已在 7.9 推翻并改为 `true`。

### 7.4 不做「行数 × forceNewRow」组合校验

曾考虑「行数超过阈值且 `forceNewRow=true` 时直接拒绝」。放弃的理由：越界与否取决于部署机的堆
大小，服务端算不出一个对所有环境都正确的阈值，写死等于替部署方猜。超量时由
`catch (OutOfMemoryError)` 转成 503，调用方得到明确提示。

### 7.5 生成路径也纳入 `max-list-rows`

`generateExcel` 走 SXSSF 流式写、成本比模板填充低一个量级，但请求体与 Jackson 反序列化出来的
二维 List 仍是纯内存占用，不限额同样能堆满。两条路径共用 `docgen.limits.max-list-rows`，
生成路径映射到 `data.size()`，填充路径映射到 `listData` 各行数。

### 7.6 容器 `mem_limit` 提到 6g

对应约 4.5 GB 堆（`MaxRAMPercentage=75`），覆盖 20 万行 × `forceNewRow=true`（10 万行实测需
2 GB，20 万行按线性外推约 4 GB）。`forceNewRow=false` 下余量充足。

这是本机实测值外推，不是生产压测结论：真实堆峰值还受列宽策略、字符串长度、是否含图片影响。
上线后应以 `-XX:+HeapDumpOnOutOfMemoryError` 的快照为准再调。

### 7.7 未采纳的方案与理由

- **服务端分页取数**：需要本服务接入数据源，改变「无状态、只认请求体」的定位，属独立议题。
- **异步任务化**（提交 → 后台生成 → 轮询下载）：工程上最正确，但需要任务表、状态机、下载端点，
  是一个完整功能，不在本次范围。
- **流式输出**：`byte[]` 改为 `StreamingResponseBody` 能省掉一份文件大小的副本，但要处理临时文件
  清理与客户端中断，会改变 HTTP 写出方式，留作后续独立改动。

### 7.8 已知残留风险

- 20 万行 × `forceNewRow=true` 在 4.5 GB 堆下按外推刚好够，实际可能 OOM。此时返回 503 而非
  静默失败，调用方可改用 `false` 重试。
- 限额默认仍为 `-1`（`docker-compose.yml` 里只有注释示例），十万条请求默认不会被拦，但也不会
  被保护——真正确保稳定需部署时显式设置 `MAX_LIST_ROWS`。

### 7.9 默认值改为 `true`：Excel 的 100 MB 单记录上限（2026-10-26 补记）

需求方反馈：6.7 万行导出后，Excel 打开提示「发现部分内容有问题，是否尽量尝试恢复」；确认恢复后，
第 2~7093 行的 24 个字段为空、只剩最后一列有值，第 7094 行起又完整。请求侧确认只有一个
`listItems`、模板一格一个占位符、无合并单元格、单 sheet。

**根因不是丢行，是产出文件超出 Excel/POI 的单个 XML 记录 100 MB 上限。** 恢复过程会丢掉它读不
下去的行，表现为「中间一段只剩最后一列」。

用 25 列、单元格文本 6 字符复现（`forceNewRow=false`）：

| 行数 | `sheet1.xml` 解压后 | 默认配置读取 |
|---|---|---|
| 60,000 | 81.7 MB | 成功 |
| 67,000 | 91.3 MB | 成功 |
| 70,000 | 95.5 MB | **失败** |
| 75,000 | 102.3 MB | **失败** |

失败时报 `RecordFormatException: Tried to read data but the maximum length for this record type is
100,000,000`。注意 70,000 行时 XML 只有 95.5 MB 就已失败——真实安全边界比 100 MB 略低。

**关键发现：`forceNewRow=true` 反而产出更小的 XML。** 它走共享字符串表，把重复文本抽到
`sharedStrings.xml`；`false` 全部内联进 `sheet1.xml`。同样 67,000 行：

| forceNewRow | 耗时 | 文件 | sheet1.xml | sharedStrings.xml | 可打开 |
|---|---|---|---|---|---|
| true | 26.6 秒 | 9.2 MB | 70.3 MB | 39.0 MB | 是 |
| false | 4.1 秒 | 5.1 MB | 91.3 MB | — | 临界 |

因此把默认值从 `false` 改为 `true`：默认值要选的是「产出能被 Excel 正常打开」，不是「最快」。
`false` 的快是用「更接近上限的 XML」换来的，大数据量下代价是拿到一个需要修复的文件。

代价是 6.5 倍耗时（4.1 秒 → 26.6 秒）。需求方确认 6.7 万行下 26.6 秒可接受。

**残留风险：** 安全行数取决于单元格文本长度、列数与数据量。67,000 行 × 25 列 × 6 字符是安全
的；若单元格文本显著更长（如 30 字符以上），`true` 模式也可能在 3~4 万行就逼近上限。服务端不做
行数拦截（理由同 7.4），由调用方按实际数据量评估。
