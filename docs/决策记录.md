# 决策记录

记录会影响后续输出的关键决策。条目编号按章节独立编号。

## 一、模板寻址收敛（2026-10-02）

### 1.1 深化 `TemplateService`，而非新建平行模块

把模板寻址收敛为一个深模块时，没有新建与 `TemplateService` 平级的 `TemplateStore`。`TemplateService`
原有 5 个方法里，除上传的校验与落盘外，其余全是对文件系统的定位与读写——它本来就是「寻址」概念的栖身
之所，只是 `WordService` / `ExcelService` 没走它。再造一个新模块只会多出一个浅模块（接口与实现几近同
宽），恰是本次要消灭的东西。

### 1.2 接口拆为读侧与写侧

最终形态为 `TemplateRepository`（读：`locate` / `read` / `list`）与 `TemplateWriter`（写：`upload` /
`delete`）。二者分开的真实理由是错误语义不同：读侧找不到文件是 `TemplateNotFoundException`，写侧收到
非法输入是 `IllegalArgumentException`。

命名规则与基路径读法仍只有一份，见 1.3 与 1.4。

### 1.3 命名规则做成不可变值对象，而非校验工具类

`TemplateName` 只由 `parse(raw, kind)` 产出，实例即「已合法」。没有沿用 `TemplateValidationUtil` 那种
`void validate(...)` 的形态——那种形态把规则集中到了一处，但未校验的名字照样能传到接口上，「合法」取决
于调用方自觉，这正是历史上三套校验并存的根因。

### 1.4 字符规则用白名单，不用黑名单

原实现沿用一个坏字符补一次的黑名单（`..`、`/`、`\`），漏掉了 Windows 盘符冒号。白名单用
`\p{L}\p{N}_.-`，中文模板名保持合法，空格与控制字符落选。

### 1.5 `.xls` 一律拒绝

事实核查结论：EasyExcel 4.0.1 对 `.xls` 模板技术上走得通（`WriteWorkbookHolder` 按扩展名推断
`ExcelTypeEnum.XLS`，`WorkBookUtil.createWorkBook` 走 `HSSFWorkbook`），但上传入口硬编码只收
`.docx`/`.xlsx`、列表入口也只列这两种——`.xls` 根本进不了模板目录，校验层的放行是死路。

且全库从未存在过 `.xls` 文件，git 历史 0 命中，测试只有一条字符串断言。据此判定它是未完成的意图而非
正在用的能力，故生成侧改判为只认 `.xlsx`。

### 1.6 `DocGenProperties` 只由读侧持有

`WordService` 与 `ExcelService` 原先持有它只为 `getTemplatePath()`，收敛后已成为接口上的假依赖，故移
除（构造参数分别从 3→2、2→1）。写侧不算目标路径，改为通过 `TemplateRepository.resolveForWrite` 取，避
免基路径读法被复制成两份。

### 1.7 上传侧沿用字符清洗，寻址侧用白名单

两侧规则刻意不同：上传的人是手里拿着文件的人，名字常带空格与括号，因一个空格拒绝整个文件不合理。由
此保证一条不变量——**凡是能落盘的名字，之后一定能在读侧被合法解析**，并有测试锁定。

### 1.8 删除 `templateExists`

生产代码无调用方（控制器四个端点均不走它），只有 2 个单元测试在用。删除它复杂度不会回来，属通过删
除测试的浅方法。

### 1.9 错误消息去掉服务器绝对路径

`TemplateNotFoundException` 原消息为 `"Template not found at: " + templatePath`，绝对路径经全局异常处
理器进入响应体，等于对外暴露服务器目录结构。改为只含模板名——模板名是调用方自己传的，回传它无泄露却
是排障必需。

### 1.10 迁移测试而非复制

穿越接缝的 5 个用例（`WordServiceTest` 3 例、`ExcelServiceTest` 2 例）平移到新测试类后删除。理由：接
口即测试面，契约由深化后的模块的测试保证；三个调用方各自保留同一条断言，只是在三个地方锁同一个事实。

## 二、载荷设施收敛（2026-10-02）

### 2.1 遍历器与转换结果提为独立模块

新增 `PayloadWalker`（遍历渲染数据树：嵌套 Map、Iterable、数组三类容器）与 `ConvertedImage`（载荷转换的
统一出口：字节 + 格式 + 宽高）。原先遍历逻辑内嵌在 `WordService.convertImagePayload`，Excel 侧另有一份
只扫顶层且 listData 分支完全不做预处理的副本。

`ConvertedImage` 提为独立类型而非让 `QrCodePayloadConverter` 反向 import `ImagePayloadConverter` 的嵌套
record，避免 util 包内不自然的横向依赖。

### 2.2 数组是遍历的独立一支

Java 中数组不实现 `Iterable`。原实现在 `Object[]` 上漏掉这一支，导致 `items[0].logo` 保持 Map 原样并
被渲染成 `Map.toString()`，与「只扫描顶层」是同一种静默失败。已补并有测试锁定。

### 2.3 Excel 侧补齐列表载荷与二维码

事实核查结论：EasyExcel 4.0.1 的 `fill(List)` 列表路径与 `fill(Map)` 单值路径走同一个 `doFill` /
`converterAndSet` / `fillImage`（`AbstractExcelWriteExecutor.convert` 判 `originalFieldClass ==
WriteCellData.class` 后原样返回），两者等价。故缺口在自身代码：`listData` 分支未做载荷转换。

二维码此前仅 Word 支持，其字节由 ZXing 本地生成、无 URL，无法走图片的 HTTP 下载链路，故为其新增字节级
出口 `convertToImage`，与图片共用 `ConvertedImage`。

### 2.4 附件响应收敛为一个模块

新增 `GeneratedDocumentResponse`，DocController 四个端点改为交出「内容 + 用户想要的文件名」。事实核查
确认 Go SDK 完全不读 Content-Disposition（`doPostRequest` 只读 body，保存文件的文件名来自调用方
`outputPath`），故无向后兼容风险。`TemplateController.downloadTemplate` 未纳入——其 templateName 已由
`TemplateName` 白名单校验，本身安全，改它属风格统一而非修复问题。

## 三、未纳入本次的已知缺陷

以下缺陷本轮已识别但未处理，留待单独排期：

### 3.1 上传非原子

`Files.copy(REPLACE_EXISTING)` 直接覆盖目标文件，并发「渲染读取 + 上传覆盖」可读到半写文件。修复会改
变 `upload` 的失败语义，需单独确认。

### 3.2 日志注入

`fileName` / `templateName` 等用户输入未做换行过滤即入日志。波及全部 controller 的日志行，超出模板寻
址这条线。

### 3.3 `GlobalExceptionHandler` 兜底处理器接管 Spring MVC 内建异常

JSON 解析失败、405、multipart 超限都会落入兜底返回 500，与文档承诺的 400/413 不符。

详见 `CODE_REVIEW.md` 对应章节。
